# ADR-0017: About を Home に統合し、Timeline はダイジェスト + 全件ページの二段構えにする

Date: 2026-09-30
Status: Accepted

## Context

ページ構成は `/`（Home）、`/work/`、`/about/`、`/timeline/` の 4 つだった。
このうち Home と About は中身が未実装のまま、役割が重複していた。

- Home と About はどちらも「自己紹介」を載せる場所であり、2 ページに割ると同じ話を 2 回書くか、
  どちらかが薄くなる。実際 #18（S17 Home content）と #20（S19 About content）は
  どちらも着手されないまま滞留していた
- Timeline（#94 / #95 / #96）は独立ページとして設計されているが、v1 時点のエントリ数は
  10 件程度の見込みで、1 ページを占有するほどの分量がない
- 一方で Timeline は ADR-0014 で日次 cron リビルドすると決めた、本サイトで唯一
  更新され続けるコンテンツである

## Decision

### ページ構成

| URL | 内容 |
| --- | --- |
| `/` | 自己紹介（日本語）+ Timeline 最新 6 件 + 全件への導線 |
| `/en/` | 同じ構成の英語版（ADR-0018） |
| `/work/` | プロジェクト一覧（#19） |
| `/timeline/` | Timeline 全件 |

- `/about/` は**廃止**する。統合先は `/` とし、nav から About を外す
- `/timeline/` は**維持**する。Home にはダイジェストのみを置く

nav は Home / Work / Timeline の 3 つになる。

### Timeline の実装

#94 の表示コンポーネントに件数上限を引数として持たせ、1 つの実装を複数箇所から使う。

```astro
<Timeline limit={6} />   <!-- / と /en/ -->
<Timeline />             <!-- /timeline/ -->
```

ソースレジストリ（#94 の `TimelineSource`）とデータモデルは変更しない。

### Work の詳細ページは作らない

`/work/` はリポジトリ一覧に留める。`/work/<slug>/` の詳細ページも、GitHub の README を
ビルド時に取得して描画する構成も採用しない。

インフラ構成図やアーキテクチャ解説を見せたい場合は、**Zenn 記事として書く**
（ADR-0012 / ADR-0014）。Timeline に自動で載り、このリポに新しいページ種別を増やさずに済む。
Work エントリ側から記事へリンクを張ればよい。

## Rationale

### なぜ About を統合するか

個人ポートフォリオの分量では Home = About が自然で、分割は「Home に何を書くか」を永久に
未決にする。統合すれば #18 と #20 が 1 つの作業に畳める。

### なぜ Timeline は URL を残すか

分岐コストは引数 1 個である一方、単独 URL は次を担保する。

1. 職務経歴書や GitHub プロフィールに「活動はここ」と貼れる安定した URL。日次リビルドされる
   唯一のページであり、Home を貼るより訴求が直接的
2. Timeline 専用の OG description を持てる。Home と共有すると自己紹介の文面になる
3. GitHub / Zenn の自動取得（#95 / #96）が入るとエントリは自然増する。Home に全件置いて
   「more」で畳む設計は、件数が 3 桁になった時点で破綻する

### 却下した案: Home に全件 + more ボタン

上記 3 の理由で却下。v1 の件数では成立するが、自動取得を入れる前提の設計としては寿命が短い。

### 却下した案: nav をページ内アンカー（`/#about` 等）に置換

Work と Timeline は実ページとして残るため、nav にアンカーと実 URL が混在する。
current 判定（#99）が複雑になる割に得るものがない。

### 却下した案: README をビルド時に取得して描画する

「自サイト内で見せた方が良い」という発想はコンテンツマーケティングや SEO の文脈では正しいが、
エンジニアのポートフォリオには転用できない。採用担当やエンジニアを GitHub に送るのは損失では
なく、**むしろ強い証拠に触れさせる行為**である。リポジトリに着地すればコミット履歴・CI の状態・
実際のコードが見える。README を自ドメインで再描画してもその証拠性は増えない。

加えて実装上の問題が揃っている。

1. **文書のジャンルが違う。** README は「使うと決めた人」への説明書、ポートフォリオのエントリは
   「面談する価値があるか判断中の人」への売り込みである
2. **相対リンクが壊れる。** README 内の相対パスは `yukit.dev/work/` から見ると無効。画像も同様
3. **見出しが衝突する。** README の `# タイトル` がページの `<h1>` と二重になる
4. **デザインが合わない。** README はバッジ・表を多用する GitHub の作法で書かれており、
   本サイトの「`border-radius` 0、影なし、65ch」方針と衝突する
5. **ビルドが他リポに依存する。** 別リポの README を壊すと本サイトのビルドが落ちる
6. **言語を制御できない。** README が日英併記の場合、`<html lang>` を正しく宣言できない
   （ADR-0018）

「同じ説明を 2 箇所に書くと drift する」という懸念は正当だが、README へリンクするだけで
解決する。エントリ側は短い売り込みに留め、詳細は README を読ませる。二重管理ではなく役割分担。

## Consequences

- #18（S17 Home content）と #20（S19 About content）を 1 つの issue に統合する
- #94（S23 Timeline）の受け入れ条件に「`limit` 引数で件数を絞れる」を追加し、成果物を
  「`/timeline/` ページ」から「コンポーネント + 複数の設置先」に変更する
- #99（nav current 前方一致）の対象は `/work/` 配下のみとなり、優先度が下がる。
  ただし Work の詳細ページを将来作るなら必要になる
- ADR-0014 の Consequences にある「nav の `Writing`」への言及は現状と乖離している。
  本 ADR で nav を再定義するため、追補または注記が必要
- `/about/` への外部リンクは存在しない想定のため、リダイレクトは置かず削除する
  （サイト未公開のため実害なし。公開後に同種の変更をする場合は `_redirects` での 301 を検討する）
- Timeline コンポーネントは `/`・`/en/`・`/timeline/` の 3 箇所から使われるため、
  設置先に依存しない設計にする必要がある
