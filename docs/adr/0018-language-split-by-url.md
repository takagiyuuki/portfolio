# ADR-0018: 言語は URL で分ける — 併記もトグルも Astro 公式 i18n も採用しない

Date: 2026-09-30
Status: Accepted

## Context

日英バイリンガル対応の方式が確定しておらず、`CLAUDE.md` の記述が自己矛盾していた。

| 出典 | 記述 |
| --- | --- |
| Goals | 「日英バイリンガル（ページ内併記方式、Astro 公式 i18n は不採用）」 |
| Stack | 「言語切替は JS toggle + localStorage、Top/About のみ対応」 |

併記とトグルは両立しない。この矛盾のため #15（LangToggle scaffold）は `needs-info` で停止し、
#20（About final content）も着手できない状態だった。

### 読者の分布

判断の前提として、想定読者を確認した。

- 読者の多数は日本語話者で、応募先も日本企業が中心
- ただし外資企業にも応募したい。英語の自己紹介があれば有利になる

つまり**量では日本語が優位、しかし英語版は目的上必須**という非対称な要求である。

### SSG での制約（実測）

インストール済み Astro 7.3.5 の型定義
（`node_modules/astro/dist/types/public/context.d.ts:427`）に明記がある。

> `Astro.preferredLocale` — This property is only available for routes rendered on demand
> and cannot be used on prerendered, static pages.

`Accept-Language` ヘッダを参照する機能であり、ビルド時にヘッダは存在しない。
したがって **Astro 公式 i18n のブラウザ言語自動判定は、本サイトの構成では使えない**。
SSG で利用できるのは `Astro.currentLocale`（そのページ自身のロケール）のみ。

## Decision

### URL で言語を分ける

| URL | 言語 | 中身 |
| --- | --- | --- |
| `/` | 日本語 | 自己紹介 + Timeline ダイジェスト |
| `/en/` | 英語 | 同じ構成の英語版 |
| `/work/` | 英語 | 共用。PRD #1 の「Work は English-only」を維持 |
| `/timeline/` | 混在 | 共用。外部取得のため統一不可 |

素の Astro ファイルベースルーティング（`src/pages/en/index.astro`）で実現する。
**Astro の i18n 統合機能・設定・依存は一切使わない。**

`/ja/` は作らない。`/` が中身を返す。

### 英語版が必要なのは `/` のみ

`/work/` は自前で書く英語エントリ、`/timeline/` は外部取得で原理的に翻訳対象が存在しない
（GitHub は英語のリポジトリ名、Zenn は日本語の記事タイトル）。
したがって翻訳する散文は自己紹介 1 枚だけである。

### 言語リンク

各ページの `<h1>` 直後に置く。`Sidebar` には置かない。`/` と `/en/` にのみ出す。

```html
<a href="/en/" lang="en" hreflang="en">Read this in English →</a>
<a href="/" lang="ja" hreflang="ja">日本語で読む →</a>
```

- テキストであり、アイコンではない
- **相手の言語で書く**
- `lang` はリンクテキスト自体の言語、`hreflang` はリンク先文書の言語。役割が違うので両方付ける

### メタデータ

`/` と `/en/` に相互の `hreflang` を出す。`x-default` は `/en/` を指す。

```html
<link rel="alternate" hreflang="ja" href="https://yukit.dev/" />
<link rel="alternate" hreflang="en" href="https://yukit.dev/en/" />
<link rel="alternate" hreflang="x-default" href="https://yukit.dev/en/" />
```

`/work/` と `/timeline/` には対応する版が無いので出さない。

### 本文の置き場

`.astro` に直接書く。`src/content/` のファイル、Content Collection、Markdown import は
いずれも使わない。

### 型で宣言する

ページがメタデータを宣言し、共有コンポーネントはパス判定をしない。

```ts
// src/types/page.ts
export interface PageMeta {
  title: string;
  description?: string;
  lang?: 'en' | 'ja';
  alternate?: { hreflang: 'en' | 'ja'; href: string }[];
  isFrontDoor?: boolean;
}
```

既定値は `lang: 'en'` / `alternate` なし / `isFrontDoor: false`。
既存の `/work/` と `/timeline/` は何も書かなくても現状の挙動を維持する。

ナビゲーションは別系統として、レイアウト Props に `homeHref`（既定 `/`）を追加する。
`/en/` のみ `/en/` を渡す。

### `<html lang>` と混在ページ

`lang` は文書の主言語を宣言する属性であり、混在を表現する手段はない。
`/timeline/` は主言語を `en` とし、**日本語のエントリのみ個別に `lang="ja"` で囲む**。

`TimelineEntry`（#94）には明示的な `lang` フィールドを持たせる。`source` からは導出しない
（GitHub リポジトリに日本語の説明を書くこともあり、ソースと言語は 1 対 1 ではない）。

### 面ごとの URL 使い分け

| 置く場所 | URL |
| --- | --- |
| 日本企業への応募書類・職務経歴書 | `/` |
| 外資への応募書類・英文レジュメ | `/en/` |
| GitHub profile / リポジトリの website 欄 | `/en/` |
| LinkedIn（英語プロフィール） | `/en/` |
| Zenn プロフィール | `/` |

## Rationale

### なぜ併記を採らないか

英語版を作る動機は「外資の採用担当に英語の自己紹介を届けること」である。
併記ページを送ると、**半分が読めない日本語のページ**が届く。段落ごとに日本語が挟まるため
英語だけを追う読み方も苦しい。目的に対して最も効率の悪い届け方になる。

逆も成り立つ。日本企業の担当者には英文が読み飛ばす対象として挟まり、スクロール量が倍になる。

加えて併記では `<html lang>` を正しく宣言できない。現在の `<html lang="en">` のまま日本語を
地の文として出すと、スクリーンリーダーが日本語を英語として読み上げ、ブラウザの翻訳機能も
誤判定する。

### なぜ LangToggle を採らないか

切替には両言語を DOM に入れる必要があるため、**ページ重量は併記と同じ**である。
そこに JS・localStorage・初期表示のちらつき・`lang` 属性の JS 書き換えが上乗せされ、
しかも英語専用 URL は得られない。併記に対して払うコストの見返りがない。

本リポは同じ判断を既に下している — ダークモードは「OS 設定に追従、ユーザートグル UI は
置かない」（Non-Goals）。言語トグルはそれと同じカテゴリの UI である。

### なぜ Astro 公式 i18n を採らないか

自動判定が SSG で使えない（Context 参照）ため、公式 i18n の実質的な価値は次の 3 つに絞られる。

1. `getRelativeLocaleUrl()` などのリンク生成ヘルパー
2. `Astro.currentLocale`
3. fallback routing（`fallbackType: 'redirect' | 'rewrite'`）

1 と 2 はページが数枚なら手書きで足りる。価値があるのは 3 だけだが、
**翻訳するのは `/` の 1 枚のみ**なので「翻訳されていないページ」が存在せず、fallback が
発生しない。設定と学習コストがそのまま無駄になる。

なお `CLAUDE.md` の「Astro 公式 i18n は不採用」が**言語ごとの URL 分離そのものの否定**と
読まれていた節があるが、両者は別の話である。不採用としたのは統合機能であって、
`src/pages/en/` というディレクトリを持つことではない。

### なぜ `/ja/` を作らないか

`/ja/` と `/en/` を対称に置くと `/` に何を置くかを決めねばならず、選択肢は 2 つしかない。

1. `/` → `/ja/` へリダイレクト。しかし **`yukit.dev` は履歴書に書く文字列**であり、
   そこがリダイレクト 1 ホップになるのは避けたい
2. `/` に言語選択ページを置く。クリックが増え、トップページに中身が無くなる

`example.com` + `example.com/en/` という unprefixed default は一般的なパターンで、
検索エンジンも通常に扱う。対称性が崩れるコストは「将来デフォルト言語を変える」
「3 言語目を足す」ときの URL 変更だけであり、本サイトでそれは起きない。

### なぜ Workers で `Accept-Language` 振り分けをしないか

`CLAUDE.md` は「SSG（動的処理は将来的に Workers Functions で追加可能）」と書いており、
Cloudflare Workers 上にあるため技術的には可能である。SSG を捨てずに自動判定を得る唯一の道
でもある。それでも採らない。

決定的な理由: **日本のエンジニアは英語ロケールの OS / ブラウザを使っている人が非常に多い。**
`Accept-Language: en-US` を送ってくる日本語話者を英語ページに飛ばすことになり、
**多数派の読者を誤った方に振り分ける**。解決しようとした問題（少数派が誤った方に着地する）
より悪化する。

副次的な問題も揃っている。

- ヘッダに応じて応答が変わるので `Vary: Accept-Language` が必要になり、CDN キャッシュの
  設計が一段複雑になる
- ユーザーが打った URL に留まれない。戻るボタンがリダイレクトと戦う
- リダイレクト回避のためにクッキーやクエリパラメータの状態管理が生える
- クローラの `Accept-Language` は不定または欠落する

代わりに 3 層で対処する。

1. 英語圏向けの文書には `/en/` を書く（主要経路であり、完全に制御できる）
2. `hreflang` + `x-default` → `/en/`（検索経由の英語話者を誘導する正規の手段）
3. ページ上部の言語リンク（誤って着地した人の脱出口）

### なぜ言語リンクを Sidebar に置かないか

4 ページ中 2 ページにしか出ない要素のために、全ページ共通コンポーネントが
「いま何のページか」「翻訳版が存在するか」を知る必要が生じる。ページ側に置けばその判断が消える。

デスクトップの sticky sidebar で常に見える利点も実質ない。日本語ページに着地した英語話者は
**スクロールする前に**言語が違うと気づくため、判断はページ上部で完結する。
モバイルでは sidebar が sticky ではないので、そもそも差が出ない。

### なぜアイコンではなくテキストか

- 国旗は誤り。国旗は国であって言語ではなく、英語にどの旗を使うのかという答えの無い問題が出る
- 地球儀は曖昧で、「言語」「国際版」「サイトマップ」を判別できない
- 実装上、アイコンを足すと `@iconify-json/lucide` を戻すことになる。PR #124 で意図的に削除し、
  PR #125 で `@iconify/tools` 由来の脆弱性ごと解消したばかりである
- 読めない人に伝えるのが目的なので、**相手の言語で書いたテキスト**がアイコンより確実

### なぜ `hreflang` が必要か

出さないと、検索エンジンは `/` と `/en/` を対応関係のない独立した 2 ページとして扱う。
主効果は**検索者の言語に応じて正しい版を検索結果に出させる**ことであり、これが無いと
英語で検索した人に日本語版が提示され得る。英語ページを作る動機を直接損なう。

重複として統合され片方が落ちるリスクは、本文が全く異なる日英では低い（それが現実の脅威に
なるのは `en-US` と `en-GB` のように内容が実質同じ場合である）。したがって `hreflang` を
入れる理由は重複回避ではなく、上記の「正しい版の出し分け」である。

Google の要件は 3 つで、いずれも満たす必要がある。

1. **自己参照** — 各版が自分自身を含む全版を列挙する
2. **相互参照** — 片方向だけでは無視される
3. **絶対 URL** — `/foo` や `//example.com/foo` は不可

1 と 2 の帰結として、**`/` と `/en/` は完全に同一の組を出力する**。異なるのは `canonical`
だけであり、各ページは自分自身を canonical に指す（他言語版に寄せると、寄せた側が
「重複であり独立した価値はない」と宣言したことになり、インデックスから落ちる）。

`x-default` は「どの言語にも一致しない訪問者に見せる版」であり、日本語話者以外には英語の方が
役に立つため `/en/` を指す。

### なぜ本文を `.astro` に直接書くか

#20 は「Markdown か TypeScript か」で比較していたが、併記をやめた時点で両案の前提が消えた。

- TypeScript 案の利点は「EN/JA をペアで構造化できる」こと → ペアが存在しなくなった
- Markdown 案の欠点は「併記のマークアップ制御が効かない」こと → 併記しない

残るのは「本文は分離するもの」という感覚だけで、4〜5 段落のページには過剰である。
`lang` 属性やリンクを必要な場所に正確に置ける利点もある。現在の `index.astro` も
本文を直接書いており、書き方として一貫する。

Work（#19）が Content Collection で正しいのは、**複数エントリで同じ構造が繰り返される**
ためスキーマが効くからである。About は 1 ページ 1 本の散文で繰り返し構造がなく、同じ機構を
使う理由がない。

文章量が増えたら Markdown へ移す。`<p>` を `.md` に移して `Content` を import するだけの
機械的な移行であり、先回りする必要はない。

### なぜ GitHub のリンクを `/en/` にするか

GitHub は既に英語の文脈である（リポジトリ名・コミットメッセージ・コードコメントはすべて英語）。
加えて誤着地の壊れ方が非対称である。

| 誤着地 | 結果 |
| --- | --- |
| 日本語話者が `/en/` | 1 クリックで戻れる。**かつ英語のまま読めてしまう** |
| 英語話者が `/` | 1 クリックで戻れるが、**その間ページの内容は一切読めない** |

読者層が混在・不明な面では、壊れ方が穏やかな方を置く。

## Consequences

- **#15（S16 LangToggle scaffold）は不要になる。** close する
- **#20（S19 About final content）は `/` と `/en/` の 2 枚を書く作業に変わる。** 現行 AC は
  トグル前提なので書き換えが必要。ADR-0017 により #18（Home content）とも統合される
- **#94（S23 Timeline）** に `TimelineEntry.lang` の追加が必要
- **#19（S18 Work）は変更なし。** Content Collection のまま
- **PRD #1 の決定 10**（「English-first、JS+localStorage トグル、Home と About のみ」）を
  本 ADR で置き換える
- `CLAUDE.md` の Goals・Stack 両方の i18n 記述を修正する（矛盾も解消）
- `BaseLayout.astro` の `<html lang="en">` 固定、`Meta.astro` の `og:locale="en_US"` 固定、
  `Meta.astro` の `isHome = currentPath === '/'` 判定、`site.description` の英語固定は
  いずれも修正が必要
- `Sidebar.astro` の `isCurrent` は完全一致のため、`/en/` にいるとき `Home` に
  `aria-current` が付かない。`homeHref` の導入で解消する。#99（current 判定を前方一致にする）
  とは衝突しない
- **英語話者がドメイン直打ちで着地すると日本語ページが出る。** これは受け入れた制約であり、
  上記 3 層の対策で緩和する。将来 SSR やエッジ処理を導入する判断をした場合は再検討の余地がある
- `/en/` は GitHub からの流入先になるため、**二軍ページにできない。** Timeline ダイジェストも
  導線も `/` と同等に揃える
