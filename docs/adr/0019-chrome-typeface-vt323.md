# ADR-0019: サイトの chrome に VT323 を使い、本文は Inter のまま残す

Date: 2026-10-07
Status: Accepted

## Context

`CLAUDE.md` の Design Rules はミニマルを宣言しており、`border-radius` 0・影なし・
gradient なし・装飾的な罫線なしで構成されている。書体は英 Inter / 日 Noto Sans JP の
2 ファミリーのみだった。

一方でこのサイトは転職用ポートフォリオであり、目的は「読まれること」だけでなく
「記憶されること」でもある。Inter + 65ch + ミニマルという構成は正しいが、同じ構成の
ポートフォリオは無数にあり、構成そのものでは差がつかない。

nav の書体を検討する中で、候補によって見た目の大きさが大きく違うことが分かった。
フォントファイルの `head` / `OS/2` テーブルを直接読んで原因を特定した。

| ファミリー     | upem | cap-height / em | Inter 比 |
| -------------- | ---- | --------------- | -------- |
| Inter          | 2048 | 0.5459          | —        |
| JetBrains Mono | 1000 | 0.5500          | +0.8%    |
| Roboto Mono    | 2048 | 0.5283          | −3.2%    |
| Silkscreen     | 1000 | 0.5000          | −8.4%    |
| Pixelify Sans  | 1000 | 0.4500          | −17.6%   |
| VT323          | 1000 | 0.4000          | −26.7%   |

見た目の大きさを決めるのは `font-size` ではなく cap-height / em である。
`font-size` を揃えても大文字の実寸は揃わない。

配信コスト（latin サブセットの woff2）も実測した。

| VT323  | JetBrains Mono | Inter（現行）     |
| ------ | -------------- | ----------------- |
| 7.0 KB | 20.7 KB        | 50.4 KB + 47.3 KB |

VT323 の値は Astro が実際に取得したファイルのサイズである。

## Decision

### 書体

サイトの **chrome（nav と footer）に VT323 を使う**。本文・`<h1>`・`<h2>` 以下の
見出しは Inter のままとする。

### サイズ

cap-height の実寸を現行 Inter に合わせて算出した整数 px を使う。

| 面     | 現行 Inter | Inter の cap 実寸 | VT323                  |
| ------ | ---------- | ----------------- | ---------------------- |
| nav    | 16.875px   | 9.21px            | **24px**（cap 9.60px） |
| footer | 15.75px    | 8.60px            | **22px**（cap 8.80px） |

**`font-size` が本文の 18px より大きくなるが、cap の実寸は本文より小さい。** これは
正しい状態であり、数字の逆転を理由に戻してはならない。

ピクセル書体なので **サイズは整数 px、`letter-spacing` も整数 px**（`1px`）に保つ。
`rem`（root 18px）だと 16.875px のような非整数になり、1px のステムがにじむ。

VT323 の字送りは全グリフ 0.400 em（真の等幅）で、一般的な等幅書体（約 0.6 em）より
細身である。

### 大文字化

nav・footer ともに `text-transform: uppercase`。**フッターの人名も含む。**
VT323 は cap が 0.40 em で、小文字はさらに低く、小文字のままでは視認性が落ちるため。
`text-transform` は表示だけを変えるので、DOM のテキストは `Yuki Takagi` のままであり、
コピーした文字列やスクリーンリーダーの読み上げには影響しない。

### current マーカー

デスクトップのみ、円のドットを `>` グリフに置き換える。モバイルはドットを維持する。
モバイルではマーカーがラベルの**下**に入るため、プロンプト記号として読めない。

### ブランドと nav ラベルの左端揃え

デスクトップでは、`.brand::before` に `visibility: hidden` の `>` を置き、マーカーと
同じ書体・サイズ・`letter-spacing` で同じ幅を確保する。`header` 全体に chrome の
フォント指定を置き、ブランドと nav が同じフォントで解決されるようにする。

`calc(1ch + var(--marker-gap))` は採らない。`1ch` は字送り（9.60px）しか見ないため、
継承された `letter-spacing` の 1px を取りこぼし、ラベル（17.80px）に対して 1px ずれる。
同じグリフを同じ方法で置けば、記号や書体やサイズを変えても追従する。

### アセットは余白なしで書き出す

`public/logo.svg` の viewBox は `-32 -32 576 576` で、インク（`0 0 512 512`）の四辺に
32 単位（5.56%、48.6px 表示で 2.70px）の透明な余白が含まれていた。これがブランドと
ラベルの揃えを光学的にずらしていたため、viewBox を `0 0 512 512` に切り詰めた。

**SVG アセットはインクの外接矩形ちょうどで書き出す。** 余白はレイアウト側の責任であり、
アセットに含めない。補正をレイアウト側（負の margin など）に書くと、アセットを差し替えた
時点で数値が嘘になる。

### nav と本文の上端揃え

デスクトップでは、nav の 1 項目目を `<main>` の最初の段落と同じ高さに揃える。
`header` の `gap` を h1 の寸法とロゴの大きさから算出する。

```css
gap: max(
  1rem,
  calc(
    var(--text-h1) * var(--leading-heading) + var(--space-h1) - var(--logo-size)
  )
);
```

現在の値で 19.35px になる。ロゴの大きさ（`--logo-size`）や見出しの寸法を変えても
自動的に追従し、`max()` はロゴが h1 のブロックより高くなった場合に間隔が潰れるのを防ぐ。

このとき上端どうしが揃い、ベースラインどうしも 0.43px の差で揃う。上端の一致は式による
必然だが、**ベースラインの一致は現在の nav のサイズ（24px）と行間（1.2）による偶然**であり、
`--text-nav` を変えると崩れる。

### footer

2 行構成にする。1 行目がソーシャルアイコン、2 行目が `© <year> <name>`。両方とも
左揃えにして、本文の左端と同じ線に置く。

- 並び順は HTML の順序で変える。CSS の `order` は使わない。見た目の順序と、
  キーボード操作やスクリーンリーダーの読み上げ順が食い違うため（WCAG 1.3.2 / 2.4.3）
- コピーライト行をページの最後に置くのは一般的な慣習であり、読み上げ順も
  「操作できるリンク → 付帯情報」の順になる
- アイコンは 24px にする。アイコン単体で WCAG 2.5.8 のタップ領域（24 × 24px）を満たす

1 行構成では、画面幅によって名前とアイコンの間隔が伸び縮みし、両者の関係が安定しなかった。

### ソーシャルアイコンの色

アイコンは `@iconify-json/simple-icons` の形状をそのまま使い、色は chrome の文字と同じ
`--foreground-muted` にする。hover では nav と同じく `--foreground` に変える。

色は専用のトークン `--social-icon`（現在は `var(--foreground-muted)` を参照）を経由させる。
サイト全体のカラーパレットを変更し semantic token を導入する予定があり、そのときに
Footer を触らずにアイコンの色だけ意味のある値へ置き換えられるようにするためである。
トークン名や割り当てる色はその作業で変わる可能性がある。

### トークンの命名

**トークン名は「どこで使うか」ではなく「何であるか」で付ける。**

- 書体は `--font-chrome` 1 本に集約する。chrome は「コンテンツを囲む常設の枠」を指す
  UI 用語である。`--font-nav` と `--font-footer` のように同じ値のトークンを 2 つ置くと、
  片方だけ変えても検出されずに食い違う
- `--font-body` は変更しない。"body text" は「本文」を指す組版用語で、場所ではなく
  概念の名前である。`--text-body` / `--leading-body` と 3 つで 1 組になっている
- 両面で共有する値は概念名（`--leading-chrome` / `--tracking-chrome`）、面ごとに違う
  実測値は面の名前（`--text-nav` / `--text-footer`）を使う
- `text-transform: uppercase` はトークンにしない。調整した値ではなく on/off の
  意思表示であり、`var()` を経由させても読みにくくなるだけである

### 制約: chrome のテキストは latin のみに保つ

VT323 に CJK のグリフは無い。chrome に日本語を入れると 1 文字ごとに Noto Sans JP へ
フォールバックし、書体とサイズが混ざる。

nav ラベルを日英共通で英語にする決定（Home / Work / Timeline）と、footer が
`© <year> <name>` のみである構成が、この制約を満たしている。
**chrome に日本語を足す変更は、この ADR の再検討を伴う。**

## Rationale

### なぜ VT323 か

1. **コスト対効果。** 7.0 KB で、内容に一切触れずにサイトの印象が変わる
2. **意味のつながりがある。** VT323 は DEC VT320 端末の表示を復刻した書体であり、
   「レトロゲーム風」ではなくターミナルの出自を示す。SRE / Platform Engineer を名乗る
   サイトの枠に置く理由が立つ。Silkscreen / Tiny5 / Pixelify Sans は pixel-art や
   ゲームの印象が強く、同じ理由は立たない
3. **リスクが構造的に閉じている。** chrome に限定する限り、本文の可読性・CJK の
   フォールバック・レイアウト・メタデータには影響しない

### なぜ chrome に限定するか

- **本文**: 65ch × 18px の散文を cap 0.40 em の表示用書体で組むと可読性が落ちる。
  さらに `/` の本文は日本語であり、グリフが無いので 1 文字ごとに書体が混ざる
- **`<h1>`**: `/` の `<h1>` は `site.author`、つまり本人の名前である。採用担当が最初に
  見る要素にレトロな様式をかぶせる判断はリスクが非対称で、戻すコストも大きい

### 却下した案: 等幅の webfont（JetBrains Mono など）

実機で JetBrains Mono とシステムの等幅書体に有意な差を感じなかった。原因は cap-height
で、JetBrains Mono は Inter と 0.8% しか違わない。**書体を変えても大きさが変わらない**
ため、20.7 KB を払って得られる変化が小さい。

### 却下した案: システムの等幅スタック（0 バイト）

OS ごとに解決されるフォントが違い、cap-height も違うので見た目の大きさが揃わない。
`font-size-adjust: cap-height 0.546` で正規化はできる（2024 年に Baseline に到達、
Chrome 127+ / Firefox 118+ / Safari 17+）が、差別化という目的に対して「安全」以外の
利点が無いため採らない。

### 却下した案: Inter の uppercase + tracking のみ

0 バイトで「ラベルらしさ」は出るが、ターミナルの印象は出ない。

### 却下した案: ピクセルアイコン（Iconify の `pixel` セット）

VT323 との様式は揃うが、GitHub と LinkedIn のロゴの**形を描き直したもの**であり、
両社のガイドラインが最も強く禁じている改変に当たる。色の逸脱とは程度が違い、一目で
「公式ロゴではない」と分かる。ライセンスも CC BY 4.0 で表示義務が生じる
（simple-icons は CC0 1.0）。

### 却下した案: アイコンを純粋な黒 / 白にする

ガイドラインには準拠するが、上記のとおりフッターで浮き、カラーパレットの変更とも
両立しない。

### 却下した案: アイコンをテキストリンク（`GITHUB` / `LINKEDIN`）にする

ロゴを使わないのでガイドラインの問題は消え、依存も減らせるが、デザイン上の理由で
採らない。他のエンジニアの個人サイトでも、ソーシャルリンクにはアイコンを使うのが一般的である。

### 却下した案: subgrid で nav と本文の揃えを構造的に保証する

親グリッドにタイトル行と本文行を定義し、sidebar と main の両方をその行に乗せれば、
`<h1>` が何行でも揃う。しかしコストが本文側にかかる。

1. `<main>` の中に `<slot />` を包む要素が必要になる
2. `h1` の `margin-block-end` を親の `row-gap` に置き換えることになり、base レイヤの
   文字組のリズムがレイアウトの都合で上書きされる
3. 行の高さが `max(ロゴ 48.6px, h1 ブロック 40.95px)` になり、h1 と本文の間隔が
   27px から 34.65px に広がる。**ロゴの大きさが本文のリズムを決める**ことになる

採用した計算式は「chrome が content に合わせる」という依存の向きであり、subgrid は
その向きを反転させる。本文が主役のサイトで払うべきコストではない。

## Consequences

- **`<h1>` が 2 行になると、nav と本文の揃えが崩れる。** 計算式は h1 が 1 行であることを
  前提にしている。崩れ方は「ずれる」であって「壊れる」ではない。現在のページタイトル
  （`Yuki Takagi` / `Work` / `Timeline` / `404 Not Found`）はすべて 1 行に収まる
- **ロゴとの様式的な緊張が残る。** `public/logo.svg` は 3 次ベジェ 356 本に対し直線
  115 本、矩形や円のプリミティブは 0 という、曲線主体の有機的なマークである。その直下に
  ピクセルグリッドの nav が来る。**ロゴは書体に合わせて作り直さない。** ロゴ（48.6px）
  が主役、nav（`--foreground-muted`）が脇役という序列を保ち、衝突ではなく意図的な
  コントラストとして見せる
- **曲線のアイコンとピクセル文字の様式差も残る。** アイコンを使い続けると決めた時点で
  受け入れた代償である
- **`rel=preload` が 3 本になる**（Inter 2 本 + VT323 1 本）。nav は最初に表示される
  領域にあり、FOUT すると字形とサイズが同時に変わるため preload は外せない。
  #23（Lighthouse ≥95）の計測はこの 3 本を前提にする
- **1px の細いステムはライト / ダークで印象が変わる。** 暗い背景の明るい文字は光学的に
  太って見える。カラーパレットを変更する際は chrome の見た目を再確認する
- **アイコンを公式の SVG に置き換える余地が残っている。** simple-icons は公式ロゴを
  忠実に再現したものだが、厳密には第三者が描き直したものである。公式の SVG を
  `src/icons/` に置き、Astro の SVG import（`*.svg` は `SvgComponent` として型定義
  されている）で読み込めば、`astro-icon` と `@iconify-json/simple-icons` を削除できる。
  今回は保留とした
- ADR-0004 / ADR-0015 の CSS-first 方針は維持される。追加したのはトークンと
  `astro.config.ts` のフォント 1 件のみで、ユーティリティクラスは使っていない
- 非技術者の選考担当に「遊んでいる」と受け取られる可能性は残る。chrome に限定され、
  本文・レイアウト・OG が従来どおりであることで緩和する。受け入れた制約である
