# ADR の書き方

`docs/adr/` のアーキテクチャ判断記録（ADR）を書くときの決まりごと。

## いつ書くか

- **実装してブラウザで検証した後に書く。** 設計の段階（grill など）では ADR を作らず、
  「実装後に書く ADR の候補」として控えておくだけにする
- 理由: 企業のプロダクトは机上 → PoC → 検証を経て、実装するかどうかを判断する時点で ADR を書く。
  個人開発 × AI では机上・実装・検証がほぼ同時に起きるため、実装前の設計は弱い。
  その段階で ADR を書くと手戻りが多くなる
- **ADR は実装と同じ PR に入れる。** 書く時期は遅らせてよいが、マージの単位は分けない。
  既存の ADR と矛盾するコードだけが main に入る状態を作らないため
- 既存の ADR の記述を覆す場合は、同じ PR で該当箇所に追補する（新しい ADR へのリンクを書く）

## 何を書くか

- **検討の結果わかった決まりごと**を中心に書く
- 「却下した案」は、選ばなかった方にも合理性があった**構造的な分かれ道**だけに絞る
  （GCP か AWS か、どのファイルが何を持つか、など）
- デザインの試行錯誤（候補を 5 つ並べる等）や検討の経緯は書かない。そこから得た原則を
  Decision に 1〜2 行で書く。会話のログのような記述は、読み直したときに追うのが疲れ、かえって混乱する
- 「今のルールの一覧」（トークン表など）は `.claude/rules/design.md` のような更新していく文書に置く。
  ADR は判断と理由だけにする
